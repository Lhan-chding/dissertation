# N4 服务器执行修订

用户在查看 N3 资源停止原因后，授权将冻结 N4 放到现有服务器执行，并单独修订资源预算。
较大 CPU 模型实验放在服务器；本机只进行实现、文件核验和轻量单元测试。

## 迁移所需执行修复

旧审计含 macOS 绝对路径。`server_transfer.py` 使用明确的路径前缀映射，逐项验证哈希，
绑定服务器文件位置；原科学文件不改写。新源码与原源码快照分别记录。

收集完成后，种子检查先证明本次 N4 的 COMPLETE、binding 和全部文件哈希，再仅排除
该已验证集合中已登记的 raw 文件，避免把自身误报为历史冲突。其他同 seed 记录仍拒绝。

`protocol.py` 同时接受原协议和固定哈希的服务器资源修订，拒绝其他参数变更。
`N3_server` 只对这个修订开放。资源预测显式传入服务器旧轨迹路径，保留旧审计原件。

## 实际执行顺序

1. 在 EEE 服务器已有项目存储下建立独立目录；不修改现有 checkout 或其他作业。
2. 上传旧 M2、N0–N3 证据、原源码快照及新执行代码，核对来源与 SHA-256。
3. 提交 `preflight` CPU 作业：模块测试、同数据/初始化核验、旧轨迹 smoke、完整资源预测。
4. 仅通过预检后创建 `N3_server`，保留选择相同的证据与服务器资源回执。
5. 提交 `execute` CPU 作业：完整 N4 收集、语义数据/初始化核验、冻结独立校准和测试。
6. 运行过程监控实际 RAM、累计耗时、结果及临时文件大小，超限保留证据并停止当前作业。
7. 核验 Slurm 状态、原始计数、预测先封存再评分、文件哈希和实际统计结果，再更新建模决定。

调度脚本 `scripts/modeling_contrast_server.sbatch` 使用 `cluster02` 的 `cpu_ok` 节点、
一个 task、不请求 GPU；不设置 `--mem` 或 `--cpus-per-task`，保留调度器默认分配。
实验本身的 8 GiB RAM 上限由运行监控检查。所有远端产物与 scratch 位于项目存储。

原 N3 的科学/条件成本门禁通过不等于最终推荐资格；N4 仍必须报告分辨率和已知事件评分基线。
历史 CPU 计时缺口不会通过迁移补成零，旧工程限制继续保留。
