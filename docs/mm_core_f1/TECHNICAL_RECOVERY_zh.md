# 抢占后的单次技术恢复

2026-10-09，本轮 Qwen3.5-9B 的基座格式检查使用了账户已允许的可抢占 QoS。
五个原始分片中，193714、193716、193717完成；193713和193715被调度器抢占。
模型、数据、模板、种子、解码配置和评分定义没有调整。

停止原始分片后，保存的回答数为41/76/75/76/76，共344条；计划总数为384。
第0分片另有一条回答已经保存，但附加字段评分尚未完整保存。
原账本记录345次生成尝试、687次附加评分前向；其中一次生成在抢占时未保存回答。
这些原始尝试及成本全部保留，不退款，不将缺失回答虚构成语义失败样本。

Slurm默认自动重排导致193715再次启动。独占的分片启动凭据立即拒绝该隐式重跑，
没有重新加载模型或生成回答；这一秒设备分配也计入成本。
193713的自动重排副本在排队状态被暂停并取消。原始计费通过`sacct -D`的全部轮次求和，
不能只读取同一作业号最后一次记录。原始worker 2日志被调度器重启覆盖的限制需如实保留；
原始回答、评分、allocation核验与调度抢占记录仍在。

恢复前登记唯一`EXPLICIT_TECHNICAL_RETRY.json`，最多一次技术恢复事件，覆盖这两个受影响分片。
它绑定原冻结、阶段计划、原启动凭据、已终止分配、原始回答/评分/请求/账本前缀，以及恢复脚本哈希。
每个恢复分片有独占启动凭据，不能在恢复再次失败后自动重跑。

恢复只完成尚未保存回答的40个原计划槽位，使用相同问题、种子、模型及图像；
已有344条回答不重新抽样。已保存但缺少评分的一条回答，直接使用其保存token补评分。
旧未确定尝试及重复评分的成本继续留账。最后以完整请求集合与原始输出哈希验证完成状态。

所有后续提交显式使用`--no-requeue`。调度改用当前账户已有权限的较稳定QoS，
按其现有余量最多同时两个单卡作业；用户指定的整体五卡上限保持不变。
GPU小时继续只作记账，不作为恢复、继续或通过的门槛。

恢复工具与新的提交脚本单独提交、记录哈希；原始运行源码及其冻结不覆盖、不重写。
该技术修复不授权额外桥接、奖励变更、筛题、MM-DEV或其他科学实验。
